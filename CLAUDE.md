# ТеМАХ — Вътрешна платформа (Tmax-store-portal)

## Контекст

Вътрешен портал за верига хипермаркети за дома в България — 18+ обекта, централен
офис, два логистични склада. Стек: vanilla JS (ES5, global scope, string-concat
HTML), Supabase (PostgREST + Storage + Edge Functions), GitHub Pages hosting.
Netlify се ползва само за тестване/staging.

- **Supabase project ID:** `xiwkdiqqplgdcrkewgtv`
- **GitHub repo:** `tenchotenev13-afk/Tmax-store-portal`
- **Production:** GitHub Pages · **Testing:** Netlify
- **Огледало:** локален Postgres сървър (Живко) — тегли през anon ключа с
  PostgREST на всеки 1–5 мин. Виж „Схемни промени".

Хора и роли: `docs/PEOPLE.md`
Каталог с повтарящи се бъгове и капани: `docs/PATTERNS.md` — **чети го, когато
дебъгваш нещо, което мирише на познато**, не на всяка сесия.

## Модули и файлове

- `shared.js` — конфиг, auth, utils (`esc`, `v`, `toast`, `fmtDate`, `today`,
  `closeModal`, `sbGet`/`sbPost`/`sbPostReturn`/`sbPatch`/`sbDelete`,
  `showModule`, `assignedStores`, `calcStatus`)

`history.js` (поз. 12), защото history.js ползва storno helper функции от kasa.js.

## Auth — не заобикаляй

Логинът и смяната на парола минават през Edge Functions `auth-login` и
`auth-set-password` (bcrypt). Клиентът **никога** не чете `users.password_hash`
или `users.history_pin_hash` — всички `sbGet('users', …)` ползват явен
`select=` списък с безопасни колони. Не добавяй заявка, която ги иска.

## ЗАДЪЛЖИТЕЛЕН процес при всяка промяна на код

1. **Винаги градя върху текущото състояние на локалния git clone**, не върху
   стар/непълен working tree — освен ако потребителят изрично не е потвърдил друго.
1б. **Проверката за LF краища е `git ls-files --eol ФАЙЛ`** — очаква се `i/lf`
   (индексът) и `attr/text eol=lf`. Старата команда
   `git show HEAD:ФАЙЛ | grep -c $'\r$'` е НЕНАДЕЖДНА: `core.autocrlf=true` е
   включено, затова `git show` прилага checkout конверсията и връща CRLF дори
   когато блобът е чист LF (веднъж даде 3548 при напълно коректен файл). Ако
   трябва суровият блоб — `git cat-file blob HEAD:ФАЙЛ`, той не минава през
   филтри. Втората половина на засадата: `grep -c $'\r$'` ВЪТРЕ в командна
   субституция `$( )` губи ANSI-C кавичките и брои ВСИЧКИ редове, не само
   тези с CR — двете грешки се наслагват и дават числа като 690 и 3548 за
   напълно чист LF файл (`echo "CR: $(… | grep -c $'\r$')"` върна 690 за
   `index.html`, чийто `cat -A` показваше само `$` без `^M`). Работното
   дърво спокойно може да е CRLF; `.gitattributes` пази
   индекса. Не „поправям" краища заради грешна проверка — това дава diff през
   целия файл вместо хирургичен.
2. Преди да предложа промяна за commit — ЗАДЪЛЖИТЕЛНО и без да чакам покана:

   ```bash
   node --check <променения файл>.js
   node .claude/skills/tmax-jsdom-test/smoke.js .
   git diff
   ```

   `smoke.js` тече ~3 секунди и зарежда всичките 22 файла заедно в реда от
   `index.html`. Хваща файл, който гърми при зареждане, и име, презаписано от
   по-късен модул. Exit code 0 = чисто. **Потребителят няма да ми напомня да
   пусна това — моя работа е.**
3. **Реални функционални тестове (jsdom), не само преглед на кода** —
   включително симулиран истински клик за бутони, не само инспекция на markup-а.
   Ползвам `.claude/skills/tmax-jsdom-test/harness.js` — **не пиша boot
   boilerplate наново**. Копирам `example.test.js` като
   `tests/<фийчър>.test.js` и пренаписвам само секциите. Новият файл се
   добавя и в списъка `TESTS` в `tests/run-all.js` — той е изричен, не
   се сканира папката, така че нерегистриран тест никога не се пуска.
   Пълното API е в `SKILL.md` на skill-а.
4. При голяма/многостранна заявка — предлагам разбивка на приоритети и
   питам за ред, вместо да имплементирам всичко наведнъж.
5. **Когато потребителят каже „не работи" — първо проверявам дали живият
   файл изобщо е актуален**, преди да търся бъг или кеш. Същата сверка се
   прави и след всеки push, който пипа портала.

   ```bash
   curl -s "https://tenchotenev13-afk.github.io/Tmax-store-portal/ФАЙЛ.js?cb=$(shuf -i1-99999 -n1)" -o /tmp/live.js
   diff <(git cat-file blob HEAD:ФАЙЛ.js) /tmp/live.js && echo "АКТУАЛЕН"
   ```

   - **`git cat-file blob`, не `git show`.** `git show HEAD:ФАЙЛ` минава през
     checkout конверсията (`core.autocrlf=true`) и може да покаже разлика,
     каквато в блоба няма — виж т.1б. Тук грешката е по-коварна, отколкото
     при краищата на реда: изглежда като провален деплой.
   - **Pages се разпространява със закъснение от секунди до минута.** Първата
     проверка веднага след push често връща стария файл. Това не е авария —
     пробвам пак след 20–30 сек, преди да вдигам шум.
   - **Маркерът за проверка трябва да е низ, който съществува САМО в новата
     версия.** Търсене на низ, който го има и отпреди, връща попадение и
     срещу непоправен файл, тоест „проверката" минава винаги. (Реален случай
     24.08.2026: `sort_order:maxOrder+1` беше избран за маркер на поправка в
     `taskTabDrop`, но същият низ стои в `submitTask` от по-рано.) Преди да
     ползвам маркер: `grep -c` срещу СТАРАТА версия — трябва да е 0.
     Това е същата грешка като тавтологичен тест, приложена към деплоя.
5б. **Кешът на `raw.githubusercontent.com` е ДРУГ механизъм, не този от т.5.**
   Пътят `/<клон>/ФАЙЛ` се обслужва с `Cache-Control: max-age=300` от edge
   възел (`X-Served-By: cache-sof…`). До пет минути след push същият URL
   спокойно връща стария файл. Капанът: **`?cb=…` и `Cache-Control: no-cache`
   НЕ го пробиват** — кешът е по ПЪТ, а query низът не влиза в ключа. Пробива
   се само с fetch по **SHA на комита** вместо по клон:

   ```bash
   curl -s "https://raw.githubusercontent.com/tenchotenev13-afk/Tmax-store-portal/<пълен-sha>/ФАЙЛ"
   ```

   Проверено на 25.08.2026 с `CLAUDE.md`: `/main/` върна 22469 байта — версия
   отпреди ДВА комита — при 25423 в HEAD, а `?cb=` и `no-cache` дадоха същия
   стар файл. Същият файл по SHA беше байт по байт идентичен с
   `git cat-file blob HEAD:ФАЙЛ`, а GitHub API за `main` вече сочеше новия
   комит: push-ът е бил наред през цялото време. Ден по-рано същото с
   `bulletin.js` при прозореца на отмятанията — изглеждаше като провален push.

   Т.5 говори за `tenchotenev13-afk.github.io` (GitHub Pages) — друг хост и
   друг механизъм, там `?cb=` върши работа. Не ги смесвам: срещу raw същият
   идиом мълчи и лъже в посока „провален деплой".
6. Минимални, хирургични промени — показвам точно diff-а, нищо друго не пипам.
7. **Търсене на едни и същи данни на повече от едно място** — при промяна на
   поле/функционалност, която може да се показва и другаде (модул + История +
   Excel износ + седмичен имейл + „Днес"), претърсвам ВСИЧКИ засегнати файлове,
   не само този, който редактирам, преди да смятам промяната за завършена.
8. **Интеграционен тест при споделени глобални функции** — когато промяна
   засяга повече от един файл (напр. kasa.js + history.js), тествам ги
   заредени ЗАЕДНО в реалния ред от index.html, не само поотделно.
9. **Проверка на съществуващи данни преди ново задължително поле/ограничение**
   — SQL проверка (Supabase MCP) колко записа биха били засегнати/невалидни,
   преди да активирам изискването.
10. **Явен чеклист преди доставка**: нов запис + редакция на съществуващ —
    тествани и двата пътя; празни/липсващи данни — fallback тестван;
    гранични случаи (точно на лимита) — тествани явно, не само типичния случай.
11. **Git операции** — `git add`/`git commit` мога да предложа директно, но
    `git push` към remote **само след изрично потвърждение** на всяко отделно
    push, дори в Auto/Accept режим. Без `--force`, без `--no-verify`.
12. **Печатните изгледи наследяват CSS-а на цялата страница.** Всички печати
    в портала се рендират в `#mod-print` вътре в `index.html`, не в
    `window.open`. Следствие: глобалните правила от `index.html` важат и
    вътре в печатната таблица и мълчаливо бият собствения `PRINT_CSS`, ако
    той не задава същото свойство изрично. Три реални случая от печата на
    бланка за разлики (19.08.2026):
    - `th{white-space:nowrap;}` (index.html:67) — заглавията на колоните не
      се пречупват и излизат извън клетките си. Нужно е изрично
      `white-space:normal;` в правилото за печатната таблица.
    - `tr:last-child td{border-bottom:none;}` (index.html:69) — бие по
      специфичност (0,1,2) срещу (0,1,1) и оставя долната рамка отворена.
    - При `table-layout:fixed` без `box-sizing:border-box` padding-ът се
      добавя ВЪРХУ зададената ширина: 10 колони × 3.2mm = 32mm повече от
      190mm, тоест последната колона пада извън листа.
    Нито един от трите не се хваща от jsdom — той не смята лейаут. Затова
    правилата се заковават поотделно в теста със закотвен регекс
    (`/\.dp-tbl th\{[^}]*white-space:normal/`), а визуалното съответствие се
    потвърждава само с реален предварителен преглед от потребителя.
    Не пипам глобалните правила в `index.html` — те обслужват всички
    останали таблици в портала.
13. **Паралелни сесии** — правилото е от 23.08.2026 и заменя по-мекия
    предишен режим, при който две сесии си делеха `main`.
    - **По репото работи само ЕДНА сесия.** Другата не пипа git — нито
      `commit`, нито `--amend`, нито `reset`, нито `push`.
    - Трябват ли две наведнъж — всяка на свой клон
      (`git switch -c sesiya-<кратко-име>`), push само в него. Сливането
      го прави Тенчо, не сесията.
    - `--amend` и `reset` върху комит, който не е мой — **забранени при
      всякакви обстоятелства**, включително „нали не е push-нат".
    - `git log -1 --format='%H %s'` НЕПОСРЕДСТВЕНО преди всеки `commit`
      или `--amend`. Сверката е по **SHA**, не по автор: двете сесии
      споделят една git самоличност (`tenchotenev13-afk`), тоест `%an` е
      един и същ за всички комити и не различава нищо. `git fetch` отпреди
      пет минути не доказва нищо — върхът може да се е сменил между двете
      команди. Дългото commit съобщение се пише ПРЕДИ проверката, за да не
      стои проверката минути преди самия комит.
    - Чужди променени файлове в дървото вече са **сигнал за проблем**, не
      нормално състояние — спирам и питам, вместо да ги заобикалям.
    - Комитвам с изричен списък файлове. Никога `git add -A`, никога
      `git commit -a`.
    - Ако добавям тестов файл в списъка `TESTS` на `tests/run-all.js`, самият
      файл влиза в СЪЩИЯ комит. Иначе CI пада с „ЛИПСВА ФАЙЛ" — локално не
      се вижда, защото файлът си стои в работното дърво.

    Защо толкова строго — **един инцидент** от 23.08.2026, видян от двете
    му страни. Това не са две небрежности на една сесия: второто действие е
    опит за поправка на първото.
    - Сесия А сверява `origin`, после пише дълго commit съобщение. В този
      прозорец сесия Б комитва и `HEAD` се премества. `--amend` на сесия А
      пренаписва комита на сесия Б и го глъща в своя („Вечерен оборот",
      стъпка 4).
    - Сесия А поправя: `reset --hard` до своя комит и `cherry-pick` на
      чуждите. Отстрани това изглежда като „някой изтри работата ми" —
      сесия Б го вижда така и на свой ред възстановява. Така
      `send-email.ts` за кратко се върна към версията отпреди поправката;
      видя се случайно, при обратно четене след деплой.

    Поуката не е „някой сгреши", а че прозорецът между проверката и
    комита е достатъчен, за да се разминат две добросъвестни сесии. И
    двете независимо стигнаха до горното правило в един и същи час.
14. **Известията от Бюлетина НЕ се пращат от браузъра.** Логиката живее в
    едж функцията `bulletin-notify`, управлява се от таблиците
    `notification_topics` и `notification_matrix` и се вика от крон 15.
    Клиентът не инициира push при зареждане на модул — нито за срокове,
    нито за промоции, нито „само този път".

    Всяко „хайде да пратим известие при зареждане" е връщане към бъг, който
    беше на живо до 27.08.2026: `autoCheckBulletinNotifications()` тръгваше
    в края на `loadBulletin()`, а защитата срещу повторение беше
    `localStorage` на браузъра на админа. Следствията са три и всяко е
    самостоятелна причина правилото да важи:
    - **тръгва според това кой е отворил портала** — двама админи в един ден
      значат две известия, а нула админи значат нула;
    - **отива до всички**, а не до обекта, чиито са задачите;
    - **няма представа колко е часът** — на 27.08.2026 в 08:50 излезе
      „📅 3 срока днес … СПРАВКА МИНУСИ (20:00), Вечерен оборот (20:00)".

    Кронът решава и трите: пуска два часа преди часа на задачата (най-рано
    08:00), само неотметнатото и само за съответния обект.

    Заковано е в `tests/no-auto-push-on-load.test.js` — зареждане на
    Бюлетина от админ при данни, които ГАРАНТИРАНО имат какво да изпратят,
    и нула извиквания на `pushToAll`. Ръчните бутони (менюто
    „🔔 Нотификации" и банерът при изтичащи промоции) си остават — човек,
    който натиска бутон, е съвсем различно нещо от таб, който се отваря.

    **При проверка с `grep` през репото задължително изключвам
    `.claude/worktrees/`** — там стоят стари чекаути, неследени от git, с
    копия на файловете отпреди месеци. Попадение оттам изглежда като върнат
    код, а не е: `autoCheckBulletinNotifications` например още стои на ред
    426 в две от тях. Важи за всяко търсене из репото, не само за това.

    ```bash
    grep -rn "ИМЕ" --include=*.js . | grep -v node_modules | grep -v "\.claude/worktrees"
    ```

```bash
node .claude/skills/tmax-jsdom-test/smoke.js .   # ~3 сек, преди всеки commit
```

## Контекстен пакет за чата

Чатът работи с копие на тези файлове, качено ръчно, и **няма как само да
разбере, че копието е остаряло** — отговаря уверено от версия отпреди
няколко комита. Оттам идват разминаванията между чата и сесията тук: аз
чета живите файлове от диска, той чете снимка отпреди дни.

```bash
npm run brief   # -> docs/BRIEF.md: CLAUDE.md + PEOPLE + DECISIONS + PATTERNS + последните 20 комита
```

- Пакетът носи най-отгоре **печат за версия** — `sha`, дата, състояние на
  работното дърво, дата на последна промяна за всеки включен файл. Това е
  смисълът на упражнението: разминаването се вижда в първото изречение,
  вместо да излезе наяве след грешен отговор.
- `docs/BRIEF.md` е **генериран и gitignore-нат** — нарочно не се комитва,
  иначе печатът в него винаги би сочил комита ПРЕДИ този, който го съдържа.
  Прегенерира се непосредствено преди качване.
- **Пакетът не е източник на истина.** Инструкцията вътре изисква чатът да
  изтегли живия `CLAUDE.md` от `raw.githubusercontent.com/.../main/` и да го
  сравни с копието, преди да отговори по същество. Така забравеният
  `npm run brief` се хваща сам — иначе е тих провал: пакетът изглежда наред
  и отговорите излизат от стар контекст. И трите включени файла се теглят
  оттам, затова сверката е възможна.
- Сверката е по колоната **„последен комит по него"**, не по `sha` на HEAD —
  HEAD се мести при всяка промяна по портала, дори когато тези файлове не са
  пипани, и би давал фалшива тревога.
- `.githooks/pre-commit` **предупреждава, без да спира**, ако `CLAUDE.md` или
  `docs/` влизат в комит, а пакетът не е прегенериран. Нарочно не е гейт —
  инструмент за човека, не проверка за кода.
- Редакциите отиват в изходния файл (`CLAUDE.md`, `docs/PATTERNS.md`, …),
  никога в пакета — той се презаписва.

## Схемни промени

- Винаги `apply_migration` (не `execute_sql`) за DDL.
- Към всяка миграция пиша и rollback SQL. Ако rollback не може да се напише —
  промяната е необратима и изисква отделно решение, не рутинно прилагане.
- **Всяка нова таблица/колона → изрично уведомявам Живко** да обнови
  `mirror-schema.sql` и `$TableColumns` в `sync-mirror.ps1`.
  Задачата не е завършена, преди да има потвърждение обратно, че е приложено.
  (Историята показва, че без това огледалото изостава с месеци и цели модули
  остават без бекъп.)

## Сигурност — текущо състояние

- Anon ключът е публичен в клиента. RLS: 30 от 45 таблици с включено RLS,
  15 без. Повечето политики следват permissive `anon_all_*`
  (`for all using (true) with check (true)`).
- `users` в момента е с **изключено RLS** и `anon` има пълни права върху нея.
  Предстои затягане с колонни grant-ове — **не пипай преди Живко да е сменил
  `select=*` в sync-mirror.ps1**, иначе огледалото спира.
- Не изключвай RLS „за да мине" — това е решение, което се записва в
  миграцията с едно изречение защо, не мълчалив заобикаляне.

## Инструменти

- **Supabase MCP** — `apply_migration` за DDL, `execute_sql` за inspection/DML,
  `query_logs` за диагностика по логовете (ClickHouse SQL срещу таблица `logs`,
  филтър по `source` — напр. `edge_logs`, `postgres_logs`, `function_edge_logs`;
  прозорецът е максимум 24 часа)
- **Edge Functions** — 9 на брой. Изходният код е в `supabase/functions/`
  (описание на всяка — в README-то там). **Репото е записът, не механизмът за
  деплой** — промяна във файловете НЕ стига до Supabase, няма CI стъпка за това.
  Деплойът е ръчен през Supabase. Затова преди редакция сверявам файла с живата
  версия (`get_edge_function`) — иначе рискувам да презапиша промяна, направена
  директно в Dashboard-а. След ръчен деплой обновявам и файла тук.

  **Деплой на `send-scheduled-report` — стъпките са фиксирани:**
  1. Комитвам файла ПРЕДИ деплоя. Репото е записът; деплой от неикомитнат
     файл значи, че никой не може да каже какво точно е живо.
  2. Обновявам `vN:` бележката в началото на файла — тя описва ЦЕЛИЯ деплой,
     не последната промяна. Ако в него влизат три неща, пишат се трите.
  3. Деплойвам с `deploy_edge_function`, `verify_jwt: true`.
  4. **Прочитам обратно живата версия** (`get_edge_function`) и отчитам номера,
     `ezbr_sha256` и кои конкретни неща съм проверил, че ги носи. Без това
     „деплойнах" е предположение — един път вече сработи деплой, чийто payload
     беше отрязан, и разликата се видя чак при обратното четене.

  `tests/report-edge-sync.test.js` заковава, че функцията не се е разминала с
  `report.js`. Пада ли — синхронизирам ги ПРЕДИ деплоя, не след.
- **SheetJS (xlsx)** — Excel import/export
- **OneSignal** — push нотификации
- **pg_cron + Edge Functions** — server-side notification scheduling

## Тон и работен стил на потребителя

Директен, стъпка по стъпка, иска потвърждение преди рискови промени,
предпочита да тества сам на живо и да докладва резултат. Не обича код
да се чупи между сесии — затова горните проверки не са по избор.
