# Регресионна проверка „стара срещу нова версия“

Ръчен инструмент (не е в `npm test`): зарежда **две версии** на портала в jsdom с **едни и същи данни** и замразен
часовник и сравнява какво виждат и какво могат да правят ролите. Ползва се след голям редизайн, за да се докаже,
че е променен само външният вид.

Какво се сравнява (за всяка роля × таб × състояние на филтрите): грешки в конзолата, наборът действия (`onclick` +
аргументи + `data-*`), заявките към базата след клик на всяко действие, Excel износът, печатът и (отделно)
генераторите на отчети от `report.js`. Табове: Клиентски, Транспорт, Стока на път, За връщане, История, Разлики, Каса.
Роли: admin, accounting, logistics, warehouse (логистичен склад), manager, kasa, supply, info.

## Как се пуска

1. **Две версии в отделни worktree-а** (никога в главното дърво), с връзка към `node_modules`:

   ```bash
   git worktree add ../wt-reg-old <стар-комит>
   git worktree add ../wt-reg-new origin/main
   # в Windows: cmd /c mklink /J node_modules ..\Tmax-store-portal\node_modules   (във всеки worktree)
   ```

2. **Снимка на данните** — само GET през публичния REST (anon ключът се чете от `shared.js` на репото, не е в
   скриптовете), последните 30 дни:

   ```bash
   REG_DATA=<папка-извън-репото> node tools/regression/fetch.js <корен на новата версия>
   ```

   `REG_NOW=ГГГГ-ММ-ДДT10:00:00` (по подразбиране `2026-10-06T10:00:00`) трябва да е **деня на снимката** — от него
   идват „днес“ и „вчера“ в двете версии.

   > **Снимката НЕ се комитва и не се оставя на диска.** Съдържа имена и телефони на клиенти. Папката е извън репото;
   > изтрий я, щом свършиш (и резултатите по-долу — печатите в тях носят същите имена).
   > REST връща най-много 1000 реда на заявка: `goods_transit` и `kasa_documents` могат да са отрязани — това важи и
   > за двете версии, но е ограничение на обхвата.

3. **Пускане по 4 наведнъж** (112 задачи = 2 версии × 8 роли × 7 таба; около 15–20 минути; всяка задача се спира
   след 10 минути; приключилите се прескачат, така че прекъснатото пускане се подновява със същата команда):

   ```bash
   REG_DATA=<папка> REG_NOW=<ден> REG_OLD=<път до wt-reg-old> REG_NEW=<път до wt-reg-new> REG_OUT=<папка-за-резултат> \
     node tools/regression/sched.js
   ```

   Една комбинация поотделно: `cd <worktree> && node <път>/tools/regression/run.js . <out.json> <роля|all> <таб|all>`.
   Не пускай 16 процеса наведнъж — „Клиентски“ става 10+ пъти по-бавен.

4. **Резултатът**: `REG_OUT/<версия>-<роля>-<таб>.json` (един файл на задача) и `REG_OUT/STATUS.log` (старт/край/таймаут
   за всяка). След това:

   ```bash
   node tools/regression/merge.js <REG_OUT> old.json new.json
   node tools/regression/compare.js old.json new.json --detail --table
   ```

   `compare.js` печата (1) матрицата с разликите по роля и таб, (2) кое състояние е подразбиращият се екран във всяка
   версия, (3) информативните разлики и (4) случаите „същият набор действия, различна кратност“ — всичко извън това е
   съвпадение. Всяка разлика трябва да се обясни с комит или да стане находка.

5. **Отчетите (`report.js`)**: `node tools/regression/reports.js <корен на версията> <out.json>` за всяка версия,
   след това двата JSON се сравняват (еднакви ключове и стойности).
   `node tools/regression/probe.js <корен>` показва какви заявки прави всеки таб (за да знаеш какви таблици да теглиш).

## Бележки

- Харнесът на проекта няма `headers.get` и `requestAnimationFrame` — `lib.js` ги добавя в двете версии (без тях
  „Стока на път“ се рендира празна и изглежда съвпадаща, без да е проверена).
- Кликът проверява първия екземпляр на всяка функция във всяко състояние, не всеки запис, и не кара действията вътре
  в модалите (бутон „Запази“ във форма).
- Ролите са синтетични (без `assigned_stores`); видимостта на табовете по роли не се проверява.
- jsdom не смята лейаут: цветове, закачени заглавия, телефонна ширина и печатен лейаут се гледат със снимки.
